## Module Framework (larger initiative)

- [x] `IOlympusModule` contract + `ModuleHost` discovery — `CoreModule`/`PlatformModule` (`Application/ModuleSystem/`) declare their own Key/Name/Description/Kind/Permissions/Menus; `ModuleHost.DiscoverModules` assembly-scans, validates dependencies (throws on missing, detects cycles), and topologically orders them. `ModuleSyncService`, `PermissionSyncService`, `RbacSeeder`, `DefaultMenuSeeder`, and the `AddAuthorization` policy loop in `Program.cs` all consume the discovered list now instead of the old static `Modules.All`/`Permissions.All`/`Modules.PermissionModuleMap`. Metadata-only — **no files were physically moved**; see note below for why
- [x] Integration Hub — `IEventBus`/`IIntegrationEvent`/`IIntegrationEventHandler<T>` (`Application/Integration/`) + `InProcessEventBus` (DI-resolved handlers, in-process, synchronous so it still participates in the caller's transaction). Built the piece that was actually justified, not the full trio speculatively: retrofitted the one real coupling found below — `TenantService.ApproveRegistrationAsync` now publishes `TenantApprovedIntegrationEvent` instead of directly constructing `User`/`Role`/`UserRole`; `CreateAdminUserOnTenantApprovedHandler` (in `Users/EventHandlers/`) reacts to it. `TenantService` no longer references `IUserRepository`/`IRoleRepository`/`User`/`Role`/`SystemRoles` at all. `ICommandBus`/`IQueryBus` intentionally not built — nothing needs them yet; add each only when a real caller does
- [x] RabbitMQ-backed `IEventBus` — the real out-of-process half of the Integration Hub above, satisfying the same interface (`Infrastructure/Messaging/RabbitMqEventBus.cs` + `RabbitMqEventConsumer.cs`, `RabbitMQ.Client` 7.x). Durable topic exchange, routing key = event type's full name; consumer reflection-discovers every `IIntegrationEventHandler<T>` (no manual registration, same spirit as `ModuleHost`) and binds one quorum queue per event type with `x-delivery-limit` + a dead-letter exchange, so RabbitMQ itself tracks redelivery attempts instead of a hand-rolled retry counter. Selected via `Integration:UseRabbitMq`, seeded by a new `--messagebroker inprocess|rabbitmq` template parameter — same shape as the existing `--cache memory|redis` (both implementations always ship; the parameter just sets the runtime default), not the file-exclusion treatment `--database` got, since there's no dead-code cost to shipping both here. Still not a transactional outbox — a publish that races a crash between DB commit and broker ack can still be lost; noted explicitly in `templates/GUIDE.md` §8
- [ ] Physical module folder restructure (`Modules/Core/*`, `Modules/Platform/*` projects) — **attempted and reverted earlier this session**, for the coupling reason the Integration Hub above now resolves. Worth reattempting: the `TenantService`/`User`/`Role` circular dependency that blocked it is gone now that the tenant-approval flow goes through `IEventBus` instead of a direct reference. Still a large, ~160-file undertaking with no live Postgres in this environment to fully verify — revisit deliberately, not opportunistically.

## .NET Template Ecosystem (future initiative)

- [x] `dotnet new olympus-multi` solution template — **restructured to match `olympus-core`'s pattern**: the live repo itself is now the template (`sourceName: "ProjectNamePlaceholder"` in a root-level `.template.config/template.json`), not a separate `templates/OlympusMulti/` copy that could drift out of sync. The whole repo — every project, namespace, filename, and config value that said `OlympusCoreMultitenant` — was renamed to the placeholder in one pass. `--cache memory|redis` remains the only exposed parameter, for the same reason as before (the only one with two real implementations); `--database`/`--orm`/etc. still deliberately absent. Re-verified end-to-end after the restructure: `dotnet new install .`, generate with `--cache redis`, build, 40/40 tests pass under the renamed identity
- [x] `--database postgres|sqlserver` — second real solution-level parameter. `Microsoft.EntityFrameworkCore.SqlServer` + a new `SqlServerAdvisoryBootLock` (`sp_getapplock`/`sp_releaseapplock`, mirroring the existing Postgres one) added; picking a provider excludes the other's package refs, DI wiring, boot-lock file, and EF Core migrations from the generated output (`sources[].modifiers[]` conditions in the root `template.json`, following `olympus-core`'s established `<!--#if (database == ...) -->` comment-marker convention). Existing 12 Postgres migrations moved unchanged into `Persistence/Migrations/Postgres/`; a fresh squashed `SqlServerInitialCreate` migration generated under `Persistence/Migrations/SqlServer/` (verified as clean `CreateTable` calls, no spurious `AlterColumn`s from diffing against the Postgres snapshot). The raw repo keeps building/running as a normal Postgres app by default — deliberately did not copy two gaps found in `olympus-core`'s version of this pattern: its design-time factory hardcodes `provider = "postgres"` even in generated SQL Server output (would always throw); ours reads an `OLYMPUS_DESIGN_TIME_PROVIDER` env var instead, defaulting to postgres. And `olympus-core` ships only Postgres-flavored migrations regardless of `--database` (would fail against a real SQL Server); ours generates a real provider-specific set
- [x] `olympus-module` / `olympus-feature` item templates (`templates/OlympusModule/`, `templates/OlympusFeature/`) — install alongside the solution template from the same `dotnet new install .`. Fixed a real bug surfaced by the restructure: both hardcoded the root namespace, so scaffolding into a solution renamed via `-n` (anything other than the raw template repo) would have generated code under the wrong namespace. Added a `--rootNamespace` parameter to both, verified against a solution actually generated and renamed to `MyErpApp` — `olympus-module -n Product --rootNamespace MyErpApp` now correctly emits `namespace MyErpApp.BusinessModules.Product`. `olympus-module -n Product` still verified end-to-end to get discovered by `ModuleHost` (not just compile). `olympus-aggregate`/`olympus-event`/`olympus-integration` not built — add when a real need for the distinction shows up

- [ ] CI smoke-test matrix across template parameter combinations — three real parameters (`--cache`, `--database`, `--messagebroker`) exist today, an 8-cell matrix; add real automation once there's a CI pipeline to run it in (none exists yet — no `.github/workflows` in this repo)
